## Данные и порядок выполнения кейса

Все деньги — целые копейки; шаг границы — 1. Обозначения: `A` — amount, `B` — баланс, `D/M` — дневной/месячный лимит, `Ud/Um` — суммы уже одобренных операций. Остатки: `Rd=D-Ud`, `Rm=M-Um`.

Базовая карта **F0**: D=10000, M=50000, B=100000, ACTIVE, срок в будущем, Ud=Um=0. Создание напрямую в CMS на `http://localhost:8081`:

```json
{"bin":"400000","cardholderName":"KONSTANTIN KARENIN","currencyCode":"643","dailyLimit":10000,"monthlyLimit":50000,"initialBalance":100000}
```

PAN берём из ответа, а не из примера контракта. BIN 400000–400004 должен быть зарегистрирован. Для несуществующего PAN выбираем корректный по Luhn номер с зарегистрированным BIN и подтверждаем GET →404; для неизвестного BIN это отдельный сценарий Switch.

Базовый запрос **R0**: POST `http://localhost:8083/api/internal/authorize`, с подстановкой фактического PAN и текущего времени сервера:

```json
{"mti":"0100","stan":"000001","pan":"<PAN F0>","processingCode":"000000","amount":2000,"currencyCode":"643","transmissionDateTime":"2026-10-08T09:00:00Z","terminalId":"TERM0001","terminalType":"POS","merchantId":"MERCH0000000001","mcc":"5411","acquirerId":"ACQ001","issuerId":"ISS001"}
```

STAN меняем между запросами. Дата в примере иллюстративна: для обычного кейса используем время стенда; подмена transmissionDateTime не является способом перевести часы сервера. Примеры MMYY на дату подготовки: предыдущий месяц `0926`, текущий `1026`, следующий `1126`, новая карта `1029`.

Общий протокол каждого денежного кейса:

1. Создать отдельную F0; PATCH задаёт статус/лимиты/баланс. Срок и история usage задаются заглушкой CMS или согласованной фикстурой БД, поскольку PATCH не меняет expiryDate.
2. Для история-зависимого кейса согласовать часы, дату операции и записи usage. В фактической БД `limit_usage` использует PAN; суммы задаются согласованно: Um — сумма daily_amount за месяц, а хранимый monthly_amount — накопительное представление этой суммы.
3. Снять B/Ud/Um и число reserve до запроса, отправить R0 с изменениями из строки кейса.
4. Проверить HTTP и бизнес-ответ, затем снимок данных. Успех: B-A, Ud+A, Um+A и один reserve. Отказ: все исходные значения сохраняются, нового reserve нет.
5. Зафиксировать результат и восстановить зависимость, если её отключали. Повторный вариант выполняется на новой карте/фикстуре.

Параметризованный кейс получает ID вида `TC-A-05/1999`: суффикс — значение варианта, требования и приоритет наследуются из строки. Проверки системы пока не выполнялись.

## Попарные наборы PICT

Модели и файлы: [описание и команды](pict/README.md), [Authorization](pict/authorization.txt), [создание карты](pict/card-create.txt). Строки CSV имеют собственные `PW-A-nnn`/`PW-C-nnn`, связанные требования и оракулы. TSV — исходный вывод PICT без дополнительных колонок. Генератор и параметры зафиксированы: Microsoft PICT3.7.4, order2, seed42.

Для Authorization A=2000. DailyRoom/MonthlyRoom/Balance1999/2000/2001 — соответственно не хватает1 коп./ровно хватает/остаётся1 коп. Реализуемость данных: D=10000, Ud=D-DailyRoom; M=50000, Um=M-MonthlyRoom, разница Um-Ud накоплена в прошлые дни месяца. Эта фикстура проверяется при управляемой дате внутри месяца; на его первом дне нужна заглушка или другая дата стенда.

Ограничения C1–C4 — выбор дизайна для изолированных отказов: неактивный статус сочетаем с будущим сроком и достаточными ресурсами; истёкшую дату проверяем на ACTIVE с достаточными ресурсами; не сочетаем два финансовых дефицита. Это не запрет комбинаций в системе. Исключённые сочетания проверяют TC-A-11/12/13 и ручные границы. BinLookup ONLINE/FALLBACK остаётся фактором во всех ветвях.

Для CardCreate FIRST/LAST —400000/400004; BAD_LENGTH —40000. SHORT —`A`, MAX_255 —255 ×A, TOO_LONG —256 ×A. RUB/USD —643/840, BAD_LENGTH —64. DailyLimit ZERO/ONE/NORMAL —0/1/10000, MonthlyLimit —0/1/50000, InitialBalance —0/100000. Все поля передаются явно. `~` в модели и CSV — маркер невалидного класса PICT, в JSON его не передаём. Ограничения изолируют один неверный формат/длину на строку; M<D допускается, поскольку обязательный контракт не содержит обратного ограничения (Q-03). Defaults, отрицательные и дробные суммы проверяются вручную.

Оракул CSV Authorization: первый непройденный шаг ТЗ, при успехе00; INACTIVE/BLOCKED имеют responseCode `UNSPECIFIED` и точную причину. Для создания: неверный формат/длина →400 без сохранения, иначе201 и свойства C-01. В каждой строке состояние `NOT_RUN`; это проектируемые тесты, не результаты вызова API.

[verify.py](pict/verify.py) перечисляет полное декартово произведение значений моделей, применяет записанные ограничения, строит множество достижимых пар и сравнивает его с наборами. Отдельно проверяет значения, дубли, ограничения, актуальность оракулов CSV и хешей в [coverage.json](pict/coverage.json). Для создания карты дополнительно требует, чтобы все 81 пары валидных значений покрывались именно валидными строками: негативная проверка не засчитывается как успешное упражнение валидных полей. Итог: 19 кейсов Authorization и 20 кейсов создания. Эта проверка не обращается к СМП.

## Вопросы к требованиям и наблюдения по коду

| ID | Неопределённость/расхождение | Как действуем до согласования |
|---|---|---|
| Q-01 | Что означает «текущая дата» и какой часовой пояс? ТЗ говорит о текущих дне/месяце, код берёт transmissionDateTime UTC. MMYY не задаёт день окончания | Для обычных кейсов часы совпадают с запросом; предлагаем действительность до конца месяца. Пограничный оракул согласовать |
| Q-02 | limit списка:50 в ТЗ,10 в OpenAPI и контроллере; минимум/максимум limit и стабильный порядок не закреплены ТЗ | Default50 ожидаем по ТЗ; default10 — расхождение. limit0/-1 и порядок исследуем отдельно |

| Q-04 | currencyCode необязателен в OpenAPI с default643, Java требует NotBlank | TC-C-05 ожидает контрактный default; подтвердить контракт и оформить расхождение при прогоне |

Статические наблюдения, требующие подтверждения тестами: в `AuthServiceImpl.authorize` баланс проверяется до лимитов (TC-A-11/12); вызов обновления usage предшествует reserve, а ошибки reserve превращаются в ответ без проброса исключения (TC-A-14); время берётся из запроса (TC-A-19). Это кандидаты на дефекты, а не заявленные результаты воспроизведения. В production-код этой практикой изменения не вносятся.
