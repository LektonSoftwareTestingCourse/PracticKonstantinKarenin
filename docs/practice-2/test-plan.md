# Практика 2. План тестирования

Автор: Константин Каренин. Версия: 1.0 от 08.10.2026. Статус: тестирование спроектировано, проверки системы не выполнялись.

## Объём и результаты

Проверяем обязательные требования [ТЗ-04](../../tz/04-authorization.md) и [ТЗ-05](../../tz/05-card-management.md). Периферийные сервисы покрываем [дымовым чек-листом и критическим путём](checklists.md). Бизнес-правила, оракулы и данные перечислены в [тест-дизайне](test-design.md); приоритеты основаны на [стратегии](test-strategy.md).

Артефакты: четыре Markdown-документа, две модели PICT, исходные TSV-наборы, CSV с идентификаторами и ожидаемыми результатами, отчёт покрытия допустимых пар и скрипт воспроизведения. Unit/API/E2E-код и отчёт реального прогона в результат практики 2 не входят.

## Среда, данные и ответственность

| Ресурс | Требование |
|---|---|
| Исполнитель | Константин Каренин: анализ, документы, генерация, самопроверка; куратор: согласование вопросов и приёмка |
| Стенд | Docker Desktop/Compose, сервисы из текущего репозитория; свободные порты из `docker-compose.yaml` |
| Основные URL | Gateway `http://localhost:8080`, CMS `:8081`, Authorization `:8083`, Logger `:8088`, Dashboard `:3000` |
| Зависимости | PostgreSQL и RabbitMQ из Compose, Bin Lookup; инфраструктура доступна и миграции закончены |
| Данные | Только синтетические карты; новую карту на каждый денежный кейс; фиксируем PAN, баланс и usage |
| Время | До прогона записать часы и часовой пояс сервера; примеры рассчитаны на 08.10.2026; тесты смены периода — управляемые часы |
| Инструменты практики 2 | Microsoft PICT 3.7.4 и Python 3 со стандартной библиотекой для проверки наборов |
| Инструменты прогона | `curl`/HTTP-клиент, SQL-клиент; далее JUnit 5, Mockito, REST Assured, Testcontainers |
| Версия | Записать commit, локальные изменения, версии образов и конфигурацию без секретов |

Базовые карты создаём по JSON из тест-дизайна, а не выбираем случайно из генератора. Статус, лимиты и баланс меняем через PATCH; срок действия и история usage требуют фикстуры БД или заглушки CMS. Схему фикстуры сверяем с миграциями текущей реализации: `limit_usage` связывается по `pan`, хотя ТЗ описывает `card_id`. Состояние после API-операции проверяем отдельно от подготовительных SQL-записей.

Для точечных отказов нужен HTTP stub/proxy: недоступность только `/reserve` при работающем GET, заданные 5xx и контроль числа вызовов Bin Lookup. Остановка контейнера покрывает полную недоступность сервиса, но не подменяет этот сценарий.

Оценки — план трудозатрат, а не затраченное время. Первые пять этапов относятся к практике 2. Перед каждым реальным прогоном: восстановить фикстуры, проверить smoke и отключить фоновые симуляторы. При исправлении дефекта сначала повторяем упавший кейс, затем смежные правила и критический путь.

## Критерии входа, выхода и остановки

**Вход в проектирование:** доступны ТЗ-04/05, контракт и правила сдачи. Противоречия можно зарегистрировать без работающего Docker-стенда.

**Готовность практики 2:**

- четыре документа лежат в `docs/practice-2/`, модели и результаты — в `pict/`;
- все обязательные требования A/C связаны хотя бы с одним кейсом или пунктом чек-листа;
- статусы ACTIVE/INACTIVE/BLOCKED/EXPIRED, границы суммы и обоих лимитов описаны;
- в каждой строке ручных кейсов и сгенерированного CSV есть ID и требование;
- реальные PICT-наборы воспроизводятся, покрытие допустимых пар — 100%, нарушений ограничений нет;
- неизвестные правила отмечены как вопросы; для них указан способ уточнения;
- чек-листы исполнения остаются незаполненными до реальной проверки.

**Вход в выполнение:** smoke проходит; данные изолированы; БД доступна для снимков; согласованы вопросы, влияющие на конкретный оракул; есть средства управления временем/зависимостями для специальных кейсов. Неопределённые кейсы можно блокировать отдельно, продолжая независимые проверки.

**Выход из будущего прогона:** выполнены все однозначные P1, все они прошли; выполнены не менее 95% согласованного набора, остальные имеют объяснение; каждое обязательное требование имеет подтверждающую проверку; нет открытых Critical/High по деньгам и решениям; smoke и критический путь прошли. Любая незакрытая неоднозначность с влиянием на P1 требует решения куратора и отражается в отчёте. Проценты — предлагаемые критерии проекта, а не показатели уже проведённого тестирования.

**Остановка:** не работает ядро, миграции не завершены, тестовые данные не изолированы либо найдено неконтролируемое изменение денег. Сохраняем свидетельства и исправляем стенд/данные. **Возобновление:** причина устранена, фикстуры восстановлены, повторный smoke прошёл.

## Учёт результатов и сдача

На кейс сохраняем: ID, требования, дату/время и версию стенда, запрос/ответ, исходное и конечное состояние, `PASS`/`FAIL`/`BLOCKED`, ссылку на дефект. Для `FAIL` обязательны ожидаемый и фактический результаты; для `BLOCKED` — конкретная причина. Сгенерированный `NOT_RUN` не означает успешный тест.

Метрики будущего прогона: число выполненных/пройденных/заблокированных кейсов, покрытие требований выполненными проверками, открытые дефекты по severity. Метрики текущего проектирования: число кейсов и покрытие допустимых пар из [coverage.json](pict/coverage.json). Покрытие пар не является покрытием кода или доказательством корректности системы.

По [правилам сдачи](../submission-guide.md) после самостоятельного коммита и push нужно приложить свой репозиторий, ветку, конкретный Actions run и содержимое артефакта в Issue эталонного репозитория с label `practice-2`. В рамках этой работы подготовлены локальные файлы; коммит, push и Issue не создаются.
