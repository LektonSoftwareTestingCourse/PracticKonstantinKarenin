# Практика 2. Тестовая стратегия СМП

Автор: Константин Каренин. Дата подготовки: 08.10.2026.

## Цель и объект проверки

Проверить, что симулятор процессингового центра принимает решение по установленным правилам, сохраняет деньги и позволяет восстановить историю операции. Главный риск — одобрить запрещённую покупку, дважды списать средства либо изменить счётчики при отказе.

В практике 2 результатом служит проект тестирования: [план](test-plan.md), [тест-дизайн](test-design.md), [чек-листы](checklists.md) и [PICT-наборы](pict/README.md). Выполнение проверок системы и автоматизация относятся к следующим практикам; в этой работе не заявляется, что сервисы прошли тесты.

Источники: [ТЗ Authorization](../../tz/04-authorization.md), [ТЗ Card Management](../../tz/05-card-management.md), [API-контракт](../api-spec.md), [OpenAPI](../api/openapi.yaml), [архитектура](../architecture.md), [правила сдачи](../submission-guide.md). ТЗ определяет бизнес-правила, API-контракт и OpenAPI уточняют форматы. Конфликты фиксируются в разделе «Вопросы к требованиям» тест-дизайна. Код помогает найти точки подготовки данных и вероятные дефекты, но не задаёт ожидаемый результат.

## Область и глубина

| Область | Глубина проверки | Причина |
|---|---|---|
| Authorization | Все обязательные правила: карта, статус, срок, дневной/месячный лимит, баланс, reserve, идентификаторы, отказ CMS и fallback BIN | Здесь принимается финансовое решение |
| Card Management | Создание, чтение, список, PATCH, soft delete, генерация, Luhn, reserve, миграции и outbox | Источник карты и состояния средств |
| Gateway, Switch, Logger, RabbitMQ | Дымовые проверки и сквозной критический путь | Ошибка передачи или сохранения обесценивает верное решение |
| Симуляторы, Bin Lookup, Notification, Dashboard | Готовность, доставка/отображение данных, одна операция | Периферийные сервисы нужны для проверки цепочки |

За рамками практики 2: разработка сервисов, полноценная нагрузка, измерение покрытия кода, UX и матрица браузеров. Для реальных платёжных сетей, PCI DSS, PIN/CVV/3-D Secure требований в обязательном учебном контуре нет. Реализованный rollback можно исследовать отдельно, но он не заменяет обязательные проверки ТЗ-04/05.

## Уровни и техники

| Уровень | Проверки | Инструменты и последующий этап |
|---|---|---|
| Статический анализ | Трассировка требований, классы эквивалентности, границы, ограничения моделей | Markdown, официальный Microsoft PICT; практика 2 |
| Unit | Порядок проверок, сравнения `<=`, изменение usage, Luhn, RRN | JUnit 5, Mockito, управляемые часы; практика 3 |
| API | JSON, HTTP, обязательные поля, CRUD и отказы | REST Assured; практика 4 |
| Интеграционный | PostgreSQL, reserve, дневная/месячная агрегация, outbox, отказ зависимости | Testcontainers, HTTP-заглушки; практика 4 |
| E2E | Покупка через Gateway → Switch → Authorization → CMS → RabbitMQ → Logger → Dashboard | Чек-лист критического пути; практика 5 |
| Нефункциональный | Конкурентные покупки, уникальность RRN, восстановление доставки | Контролируемые параллельные запросы; практики 5–6 |

Классы эквивалентности сокращают однотипные проверки, границы обнаруживают ошибки сравнения, pairwise проверяет сочетания факторов. В PICT-наборе финансовые отказы изолированы; ручные тесты дополнительно совмещают ошибки, чтобы проверить приоритет правил. Проверка двух факторов не доказывает отсутствие дефекта в трёх и более факторах.

Основную массу проверок размещаем на unit/API-уровнях. E2E оставляем для денежных инвариантов и доставки результата: такая проверка дороже, зависит от нескольких сервисов и асинхронного журнала.

## Приоритеты и риски

P1 — ошибка решения или денежных данных; P2 — нарушение контракта, генерации или восстановления; P3 — периферия и диагностическая информация. Severity дефекта определяется последствиями, priority — порядком исправления.

| Риск | Вероятность / влияние | Приоритет | Как обнаружить или снизить |
|---|---|---|---|
| Баланс проверяется раньше лимитов, меняется первый код отказа | Высокая / высокое | P1 | TC-A-11, TC-A-12 совмещают недостаток средств и превышение лимита |
| Usage увеличивается до reserve и остаётся после отказа CMS | Высокая / высокое | P1 | TC-A-14: сравнить БД до и после ошибки только на `/reserve` |
| Месячный usage учитывает лишь текущий день | Средняя / высокое | P1 | TC-A-08 с расходами в разные дни и предыдущем месяце |
| Смена суток/месяца, выбор времени из запроса | Высокая / высокое | P1 | TC-A-09/10/19; согласовать часовой пояс, не подставлять дату клиента вместо часов стенда |
| Два reserve списывают повторно или конкуренция даёт отрицательный баланс | Средняя / высокое | P1 | TC-C-20/21 и TC-A-17, разные RRN и синхронный старт |
| Soft delete оставляет карту доступной операциям | Средняя / высокое | P1 | TC-C-12 и CP-12: GET, список, авторизация и reserve после удаления |
| Событие сохранено без карты либо теряется при падении RabbitMQ | Средняя / высокое | P2 | TC-C-23/24: транзакционность outbox и достижение терминального статуса |
| Общие тестовые карты и случайные статусы генератора дают нестабильный результат | Высокая / среднее | P2 | Новая карта на кейс, управляемые фикстуры; генератор проверяем отдельно |
| Код HTTP и значения по умолчанию различаются между источниками | Высокая / среднее | P2 | Q-02/Q-04/Q-05; зафиксировать контракт перед прогоном |
| Logger обновляется позже ответа клиенту | Высокая / среднее | P2 | Опрос по RRN с ограниченным ожиданием, сохранение фактической задержки |

Для всех денежных операций сравниваются не только ответы, но и состояние: баланс, usage и число резервов. Для асинхронной цепочки фиксируются RRN, PAN и время, выполняется опрос до 10 секунд. Это бюджет тестового ожидания, а не заявленный SLA системы.

## Организация результата

Каждый тест имеет ID и ссылки на требования. Исходный статус — `NOT_RUN`. При выполнении сохраняются запрос, ответ, снимки состояния, версия стенда и фактический результат; падение превращается в дефект с воспроизводимыми шагами. Неопределённый оракул помечается `BLOCKED_REQUIREMENT`, а не выдумывается по текущей реализации.

Сдача — четыре документа и каталог `pict/` по [submission-guide](../submission-guide.md). Критерии готовности проекта тестирования отделены от критериев успешного прогона в плане. Стратегия пересматривается при изменении обязательных требований или обнаружении нового денежного риска.
