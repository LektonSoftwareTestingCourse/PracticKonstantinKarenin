# В. Классификация кейсов практики 2

Исходники: [ручные кейсы и требования](../practice-2/test-design.md), [PICT Authorization](../practice-2/pict/authorization-cases.csv), [PICT создания карт](../practice-2/pict/card-create-cases.csv). Всего **82 логических кейса**: 19 TC-A, 24 TC-C, 19 PW-A и 20 PW-C. SM/CP — обзорные чек-листы, они повторяют часть сценариев и отдельно в знаменатель не входят.

## Правило распределения

Уровень выбирается по проверяемому правилу и необходимому оракулу. Ручной HTTP-запрос можно перенести в вызов класса, если цель — бизнес-ветка. Если проверяется сам HTTP-код/JSON, нужен API. Если результат определяется SQL, блокировкой, commit или реальной доставкой сообщения, нужен integration. E2E нужен для результата через всю бизнес-цепочку; в исходном наборе детальные TC-A/TC-C вызывают сервисы напрямую, поэтому автоматического отнесения всех покупок к E2E нет.

Смешанный кейс получает один уровень для самого требовательного из своих основных утверждений. Поэтому TC-A-04 со статусами, датами и успешным изменением usage остаётся integration, хотя отдельные ветки уже можно проверять unit. Отсутствие вызовов записи в раннем отказе допускается доказать Mockito; это не утверждение о rollback БД. В варианте «удалённая карта» TC-A-03 unit проверяет реакцию Authorization на 404 CMS, а фактическое скрытие DELETED сохраняет TC-C-12.

В PICT Authorization значения ONLINE/FALLBACK задаются double BinLookupClient; реальный HTTP, таймаут и число попыток проверяет TC-A-16. Сам попарный набор проверяет сочетания карточных условий, а не повторяет сетевой контракт 19 раз. Все оракулы и нерешённые Q из практики 2 сохраняются. Для API с mock сервисом успешное сохранение дополнительно подтверждают integration-кейсы, а не ответ заглушки.
